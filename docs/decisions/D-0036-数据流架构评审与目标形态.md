## 0. 摘要

**判词：不是最优解，但方向是对的。**

这套系统最值钱的是边界：发现层与钱径物理分离、SG 独占毕业/执行/账本、
提案是唯一动作桥、发现层无 venue 写钥、价格只准 WS 流、陈=不存在。这些是
骨架，不应在本轮讨论中推翻。

问题集中在两处：

1. **桥面被做成了自研双向 CDC**——LISTEN/NOTIFY 当队列、ts 当游标、
   自然键译 id、全表对账当自愈、`fin_proposal` 的 state 列组跨库双主。
2. **状态表规则杀过头**——原始高频行情不存是对的，但派生信号/评估/拒因的
   历史也一起覆盖了。这是唯一“今天不做、明天补不回来”的资产损失。

一句话：**分域的收益是隔离，成本是分布式一致性；现在成本没有被压到最小，
因为桥做成了“双库表镜像”，而不是“单向事件投递”。**

本席建议的目标形态：

- 保留双机分域；
- 桥只搬“发现层产物”，不搬全宇宙原始行情；
- 用持久 outbox + ack 替代 NOTIFY + ts 水印 + 全表对账；
- 提案/评估用自包含身份，不做跨库 id 译码；
- SG 本地订阅钱径所需价格，投影降为 repair；
- 历史走 `arch_*` change-only + 保留期；
- review 归 SG，或至少把“判决”与“钱径状态应用”拆开；
- 权限四角色最小化，环境变量正名。

1. **发现层与钱径物理分离**：采集/蒸馏/研究在 OCI，执行/风控/账本在 SG。

4. **发现层无 venue 写钥**：只读钥经 readcred 内存取，主权钥/交易钥不出 SG。
5. **价格源律**：价格只准 WS 流径行，REST 只准条款/目录注册面（T-0171）。
6. **失效语义**：数据陈=不存在，读败=fail-closed，歧义单=禁造仓。
7. **技术栈克制**：Go + ConnectRPC + PostgreSQL/TimescaleDB，单二进制，无多余中间件。

## 3. 缺陷清单

### P0-1　历史资产被“状态表”规则误杀（不可逆）

**事实（码面）**

- `md_signal` 建表注释直接写“禁时间序列化”，PK=`(kind,key)`
  （`migrations/md_1057_md_signal.sql:1-8`）。
- `md_ticks` PK=`(venue,inst_id)`、`md_mark_index` PK=`(venue,inst_id,channel)`
  （`migrations/md_1049_md_state_tables.sql:12-34`）。
- `fin_opp_eval` 被 T-0126/md_1053 改成 `UNIQUE(inst_id,template,direction)`
  的最新态（`migrations/md_1053_eval_state_table.sql:1-7`）。
- `fin_eval_reject` 也是 `UNIQUE(inst_id,template,direction,reason)`
  （`migrations/fin_0068_fin_eval_reject.sql:7-16`），同键同因只留一行。

**冲突（图面）**

D-0018 §2 明说“fin_* 审计/评估史表（opp_eval/proposal/cashflow 等）
不受本裁约束——它们行小且是事实史，天然留”。T-0126 的止血有现实理由
（25k 行/分、9GB/日），但它把 eval 从“事实史”改成了“最新态”，没有 D 档
收口。今天是两张纸各说各话。

**后果**

- 每天的唯一信号、评估、拒因历史被覆盖；
- 复盘只剩 `fin_review` 的单点判决，无法做“当时信号→后来结果”的校准；
- P5 的 `fin_opp_eval` 资产层没有历史可卖；路线图自己写“现库全为有界
  状态表=无可售资产”。

**这是唯一不可逆的缺陷。** 修法不是恢复全量 tick（会重演 1.2GB/日），
而是分层：

| 层 | 存不存 | 形态 |
|---|---|---|
| 原始 tick/mark | 不存全量 | 活跃集日快照/按需采样 |
| 蒸馏 signal | **存变化** | `arch_signal` append-only，change-only |
| 评估 eval | **存变化** | `arch_eval` append-only，verdict/net_apr 变才写 |
| 拒因 reject | **存变化** | `arch_eval_reject` append-only |
| 决策/账本 | 已存 | `fin_proposal/fin_review/fin_*` 现状 |

建议先上 signal/eval/reject 三张 `arch_*`，再做活跃集行情日快照；
保留期先定 180d，可配置。`arch_*` 只写不读决策路径。

**验收锚**

- 任取 24h，能重建某 key 的 signal/eval 变化序列；
- `arch_*` 行数随“变化次数”增长，不随 tick 数线性增长；
- 决策/执行/风控路径零 `arch_*` 读（grep 机检）；
- 归档写入失败不阻断主写径（异步/旁路，告警可见）。

> **〔ZC 意见 2026-10-28〕赞成定为 P0，另加三条硬性收口：**
> 1. **D-0018 §2 豁免必须显式废止**：本席亲证两纸冲突属实——`D-0018:50-51` 明写 eval 豁免，`md_1053` 注释自辩「正本建库即状态表形」却未走 D 档。本稿定稿时应**同 commit 出 D-0018 修订**（豁免条改指 arch_* 分层），否则「两纸各说各话」原样传给下个 session。
> 2. **arch_* 落地即改 PG-md 备份面**：§1.2 载 PG-md 备份现仅「schema+config」——arch_* 上线当天不进备份=归档资产裸奔，备份策略变更应写进本阶段验收锚（稿面漏了这条，建议补）。
> 3. **范围答§7.1：全 kind 不筛**。md_signal 行数≈标的×kind 有界，change-only 量级极小；按「消费过的 kind」筛=消费集漂移时重演「今天不做明天补不回来」——正是本条 P0 要治的病。保留期 180d 起步、配置化，90d 拿实测行数复裁。活跃集行情日快照：做，几百行/日成本可忽略。

### P0-2　同一行两个家（已出实害）

**事实（码面）**

- `fin_proposal` 载荷在 md，state 列组在 SG；前向投影不写 state，反向
  `repairProposalStates` 回写（`internal/projector/ops.go:192-249`）。
- `eval_id` 要按自然键译 SG 发号（`internal/projector/evalmap.go:16-64`）。
- `uEval` 用 `ON CONFLICT(inst_id,template,direction)`，PK 撞时
  `max(id)+1` 另发号（`internal/projector/mirror.go:121-130`）。
- 启动守卫 `setval(sgMax+1000)` 自抬 md 序列（`internal/projector/reconcile.go:28-45`）。

**实害（票面/经验库）**

- T-0169 切窗 research 直写 SG 13min，5 条提案落错库、2 个 id 撞号；
- T-0211 记录“dev→OCI 迁期 10 行 + 研究臂 509 行同键异 id，手工归位各救一次”；
- T-0195 序列守卫撞平，重启即崩环，靠 setval 抬位解。

**根因**

不是某个 bug，是模型问题：**一行提案的身份跨两个库，靠收敛启发式维持。**
“一事实一处存”在行级被破坏。

**建议**

- 提案消息自包含：`proposal_uid`（UUID 或 `(origin,id)`）+ payload；
- SG 建 `fin_proposal_admission(proposal_uid, state, retire_reason, retired_at, ...)`，
  admission 态只归 SG；
- md 侧不再承载“被回写的 state”，研究去重读 admission 的只读副本；
- eval 用 `eval_uid`/自然键，不做 id 译码；删除 `max(id)+1` 与序列守卫；
- 不建跨库 FK。

**验收锚**

- 投影臂重启/杀连/双实例（测试环境）不产生重复提案、不撞 id；

### P1-1　投递不是持久日志

**事实（码面）**

- `internal/platform/events/events.go` 的 LISTEN/NOTIFY 只是唤醒，不持久；
  断线重连后没有“从哪继续”的日志。
- `internal/projector/reconcile.go:191-200` 的 liveness 把水印夹到
  `now-10min`：`wm = max(wm, now-10min)`。当触发器漏帧（T-0194 已证触发器
  会在表重建中丢失）或监听半死时，早于 10min 的行会被永久跳过。
- 启动 `Reconcile(true)` 做全表 id 集差/全量 ts 重拉，是 O(N) 兜底，不是
  常规路径。

**影响**

- 低频表（dcd 目录、macro、funding 结算拍）可能长期停在旧值；
- 桥面故障只能靠“全表对账 + 告警”发现，滞后且不可重放；
- 每加一张桥表就多一套触发器/水印/重刷逻辑，故障面线性增长。

**建议**

PG-md 建 `bridge_outbox`：

```
seq bigserial primary key,
kind text not null,          -- proposal/eval/signal/dcd/macro/...
key text not null,           -- 幂等键
payload jsonb not null,      -- 自包含消息
created_at timestamptz default now()
```

consumer 按 `seq > ack` 读，单事务 apply + 写 `bridge_ack(consumer, seq)`；
重复 apply 幂等；`lag = max(seq) - ack` 进健康板。全表对账降为手动修复
工具，不做常规路径。若不想自建 consumer，可对 outbox 做逻辑复制（表是
append-only，无动态谓词问题）。

**验收锚**

- 杀 projector 于写批中途，重启后零丢行/零重复；
- 断线 30min 后追平，`lag` 可见并归零；
- 启动不再全表扫；单表故障不拖垮其他表；
- outbox 有保留/分区策略，不无限膨胀。

> **〔ZC 意见 2026-10-28〕裁§7.3：单表 outbox + 自建 consumer + 批级 ack；但分双车道，勿一套机制硬套两种语义。**
> 1. **事实道（proposal/eval/signal/dcd/macro/config/roster）**：逐行 outbox（同事务触发器写入——复用既有 ev_* 触发器位改造，写径零改动），payload 自包含 uid。触发器丢失（T-0194 表重建丢触发器）用 T-0223 同款机检根治：schema 断言「桥域表 × outbox 触发器存在」差即红，比稿面「手动修复工具」更闭环。
> 2. **ts 态镜道（ticks/mark/funding）**：这些是 latest-wins 状态镜，逐行 outbox=热表写放大翻倍（有违 B 原则「成本压最小」）。保留「持久化 per-channel 水印 + 有界拉取」机制即可，但**删掉 `now-10min` 夹逼**（本席亲证 `reconcile.go:191-200`，正是丢行病灶）、水印落表持久化、liveness 告警保留。事实要日志、状态要水印——两种语义两种机制，比强归一更简。
> 3. **逻辑复制弃**：slot 管理/WAL 滞留是经典运维坑，可观测性差于「一张表+一个计数器」，且引入升级面摩擦；自建 poller 百行级，符合架构约束 §1 技术栈克制。ack 粒度=批级（单事务 apply 成功即 ack=max(seq)），行级/表级 ack 皆无增益。

> **〔DV 意见 2026-10-28〕附议双车道+per-kind 游标（优于毒丸隔离），补两点：**
> 1. **per-kind 游标引入跨 kind 应用序缺口**：单 seq 空间+按 kind 分游标=不同 kind 的 apply 相对序不再保证。若 proposal 帧的消费对 eval 帧的落库有依赖（引用对拍/去重），per-kind 快道会把 proposal 推到 eval 前面。解法二选一：payload 完全自包含（消息内嵌引用快照，稿面「自包含」本意推到底）；或 consumer 声明跨 kind 依赖序（如 eval 游标须 ≥proposal 帧关联水位）。定稿时钦定其一写入消费契约，勿留给实现默认。
> 2. **触发器写 outbox 同受 T-0194 疤**：ZC 案「ev_* 触发器位改造」与 CC「NOTIFY 同 commit 摘除」都成立，但仍依赖触发器在场——existence 闸（P0-1 块同款）+consumer lag 告警是 outbox 径自己的两条保险，入本阶段锚。

## 4. 目标形态

```
OCI: collector + research + PG-md + bridge_outbox + arch_*
      │  outbox(seq, kind, key, payload) → ack/lag（幂等、可重放）
      ▼
SG:  core + review + PG-fin + 本地 WS 活跃集(tickers/mark/index/funding) + MT5
      proposal 载荷: md 正本；admission/state: SG 正本；无跨库 FK
```

### 4.1 五条原则

1. **桥只搬发现层产物**：proposal payload、eval（可选）、signal（只搬消费的
   kind）、dcd catalog、macro；不搬全宇宙 ticks/mark/funding。
2. **一份事实一个家**：提案载荷归 md，准入态归 SG；eval 用 uid；不译 id。
3. **钱径价格全本地**：SG 订阅覆盖已有仓所需价格，桥死不影响守卫/估值/平仓。
4. **历史 change-only**：原始高频不存，派生状态变化存；`arch_*` + retention。
5. **权限最小化**：四角色、一个 env 文件、`MD_PG_DSN` 正名。

### 4.2 事实归属矩阵（讨论底稿）

| 事实 | 正本 | 副本/消费 | 桥向 | 备注 |
|---|---|---|---|---|
| 行情 tick/mark/funding | md | SG 活跃集镜像/本地共写 | md→SG | 只搬活跃集，桥死有本地生存线 |
| 蒸馏 signal | md | SG 精选 kind | md→SG | `arch_signal` 存变化 |
| 评估 eval | md | SG 被提案引用行 | md→SG | `eval_uid`，不做 id 译码 |
| 提案 payload | md | SG 只读 | md→SG | append-only |
| 提案准入态 | SG | md 只读副本 | SG→md | 独立 admission 表，字段级双主取消 |
| 策略/持仓/执行/账本 | SG | md 只读副本（研究去重） | SG→md | 副本禁写 |
| review 判决 | SG | md 只读（如需要） | SG→md | 甲案 review 回 SG |
| config/roster | SG | md 副本 | SG→md | 现有第九桥/直 beat |
| 历史归档 | OCI | 无 | 只写 | 不进决策查询 |

## 6. 分阶段方案

### Phase 0　归档径（P0，先做）

- **范围**：`arch_signal`、`arch_eval`、`arch_eval_reject`；活跃集

## 9. 风险与回滚

- **归档**：写放大/延迟——change-only + 批量 + 旁路告警；失败不阻断主写。
- **outbox**：at-least-once——消费端幂等；ack 只在 apply 提交后写；重复
  apply 用 uid/自然键去重。
- **review 迁移**：双跑对拍一周；判决不一致以 SG 侧为准；保留旧径回滚。
- **权限收窄**：先审计现有 SQL，再收权；`BEGIN;...;ROLLBACK` 探针验收；
  避免误伤 report/earn。
- **dualwrite 终切**：保留 `O_CORE_IMAGE`/env 回滚径；终切窗口避开发布窗。
- **不做大爆炸**：每阶段独立验收，前一阶段不绿不启下一阶段。

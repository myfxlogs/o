# 无头决策席冷启动与批次隔离讨论稿

> 状态：讨论稿，供另一席评估；尚未形成决策或施工授权。
> 范围：只讨论降低无头决策席重复冷启动成本，同时避免票间争抢与状态串扰。

## 1. 背景与现状

当前无头决策席由事件唤醒为主，另有 30 分钟兜底 timer。`o-decision-seat.service` 是一次性批次：`dm_tick.sh` 先查待裁事项；没有待裁时跳过 Devin 模型调用，但仍执行零 LLM 的施工派单/限流续跑检查。有待裁时才运行 `devin -p`。

决策调用没有显式续接既有 Devin 会话，因此每个有待裁的批次都会新启一个模型调用。事件密集、批次刚结束又有事件到达时，可能出现连续冷启动。空拍不调用模型，但当前没有面向决策模型调用次数、每批耗时和 token 用量的完整量化报表。

施工席已采用另一套隔离机制：每票一个 `o-worker-<票号>` 瞬态 unit、独立 Devin 会话与运行目录，并由统一调度闸限制额度和并发。本文不建议改变施工席的一票一 run 约束。

## 2. 目标与边界

目标：

- 减少短时间内重复启动决策模型的次数。
- 保持单一决策席串行裁决，禁止同票被并发合并、翻票或重复裁决。
- 每票结果、理由、事件记录仍可独立追踪；一票失败不能把其他票误标完成。
- 失败可见，恢复后能从未完成票继续。

边界：

- 不以长期共享会话作为默认方案。会话历史可能增长并串入前票上下文；续接是否节省 token 也需实测。
- 不改变席位权序、红线升件条件、施工并发上限和票面验收标准。
- 本稿不授权修改脚本、服务、数据库或席位协议。

## 3. 建议讨论的方案：合并唤醒、单飞批次、逐票落账

### 3.1 合并短时事件

事件到达时先唤醒轻量调度层并标记队列有变化；在短暂 debounce 窗口后启动一次决策批次。窗口内的新事件并入同一批。30 分钟兜底继续保留，确保事件漏送后仍会扫描。

Debounce 只合并短时突发，不应成为长等待。具体窗口（例如 15–30 秒）由讨论席按实际事件密度和响应时限确定。

### 3.2 单飞与固定队列快照

每次批次开始时取得决策席单飞锁，并记录待裁队列快照：票号、最新事件 id/时间、当前状态。按既定队列顺序逐票处理。批次开始后新到的票留给下一批，避免队列在执行中漂移。

若已有批次持锁，新唤醒只留下“队列有变化”的信号，不再启动并行决策模型。当前批次结束后，调度层检查该信号并安排下一批。

### 3.3 一次模型调用处理一批，票仍逐张裁

讨论是否由一次新鲜模型调用读取一组待裁票，并按票号逐张核查、逐张给出闭集裁词。禁止把多票揉成一个共同裁决：每票必须有独立的范围核查、验收锚对账、理由和落账动作。

每完成一票即持久化该票裁决/完成事件和票面状态，再进入下一票。若模型或工具在中途失败，已完成票保持完成；未完成票留在待裁队列，下次批次只处理剩余票。这样批次共享一次冷启动成本，但处理状态仍按票隔离。

### 3.4 幂等与恢复

- 每票处理前复查最新事件和票状态，已被其他合法路径处理的票跳过。
- 只有成功写入本票裁决结果后才释放该票；处理中断不得写成完成。
- 单飞锁使用带过期时间的 lease，异常退出后可恢复；接管前复核最后一条事件，避免旧批次迟到写入。
- 通过 `ops_event` 的事件 id/水印确定快照边界，避免同一事件被重复消费。
- 保持升件规则 fail-safe；升件票可独立落升件后继续处理后续合规票，或按审议结果停止整批，需明确裁定。

## 4. 主要取舍

### 优点

- 事件突发时，多张待裁票可能共享一次模型冷启动。
- 单飞锁、固定快照和逐票落账能避免决策席自身并发撞车。
- 批次中途故障时可从未完成票续处理，不回滚已完成票。
- 不依赖长寿命对话上下文，减少跨票历史污染风险。

### 风险与成本

- 一批票越多，单次上下文越大；token 总量未必下降，需设置每批票数/上下文预算上限。
- 一票的异常可能拖慢同批后续票；逐票 checkpoint 可限制影响，但不消除批次耗时。
- 锁、lease、水印与幂等写径增加状态机复杂度，错误实现会造成漏裁或重复裁。
- 若主要成本来自每票自身的大量 diff/证据，而不是冷启动固定成本，批处理的节省可能有限。

## 5. 备选方案

1. **只做 debounce + 单飞，不合批**：改动较小，减少事件风暴重复启动；每批仍只裁一票或按现行行为执行。适合先做低风险试验。
2. **决策席长期续接会话**：表面上减少进程冷启动，但历史上下文可能累积、跨票污染，且 token 是否降低未知。不建议作为第一阶段。
3. **轻量常驻队列协调器，模型按需启动**：协调器只做事件合并、锁和水印；仅队列非空时起模型批次。结构清楚但运行组件更多，需评估运维成本。

## 6. 建议的评估顺序

1. 先采集一段时间基线：事件唤醒数、service 实际启动数、空拍数、模型调用数、每批待裁票数、token 用量、失败/重试数、待裁最长等待时间。
2. 若重复启动主要来自短时事件突发，先试 debounce + 单飞；保留 timer 兜底并验证不会丢唤醒。
3. 若一批常有多张待裁且冷启动占比明显，再做固定快照、逐票 checkpoint 的合批原型。
4. 用回放覆盖：重复事件、处理中新增票、批次中途退出、锁过期接管、升件、已完成票重放、模型限流。
5. 对比优化前后的 token/票、冷启动/票和最长等待时间；任何成本下降都必须同时满足零重复裁决、零漏裁和事件留痕完整。

## 7. 交给讨论席的待决问题

- 当前 token 消耗中，模型冷启动固定成本占多少？实际每个 service 批次是否都会调用 Devin？
- 队列里多票同批处理的最大票数或上下文预算应设多少？达到上限后如何切批？
- 是否接受短暂 debounce；业务对新票裁决的最大等待时间是多少？
- 升件是否只暂停该票，还是停止整个批次？
- 是否先实施低风险的观测、debounce 和单飞，再依据数据决定合批？

# T-0226 部署径 SG 侧补强——compose 同步/CPU 上限/裸容器残骸

> 状态：待施工 | 优先级：P1（部署唯一径三处实坑，下次部署必撞）
> 立项：决策席 @ 2026-10-28（T-0215 实部取证）

## 背景——T-0215 实部 ab62c2f 撞出的三坑

1. **SG compose 文件不被部署径同步**——`deploy_image.sh` 只运镜像，`ssh sg "cd /opt/o && O_CORE_IMAGE=… docker compose -f docker-compose.yml -f docker-compose.sg.yml up -d o-core"`。SG `/opt/o` 非 git 仓，compose 文件是手工副本，仍是 T-0217 前的 `image: o-core:latest` → `O_CORE_IMAGE` 环境静默失效 → `.Config.Image` 永远 latest，**产地锚结构性落空**。本次靠手工 scp 齐文件才补上。
2. **`docker-compose.yml` o-postgres `cpus: 8` vs SG 盒 4 核**——compose 起任意服务时连带评估依赖 recreate，o-postgres 命中 `range of CPUs is from 0.01 to 4.00` 硬拒。当前 `up -d o-core` 必炸 postgres recreate，只有 `--no-recreate`/`--force-recreate o-core` 绕行。下次部署脚本直接踩。
3. **裸 `docker run` 残骸占容器名**——T-0217 前手工径留的无 compose 标签 `o-core`（04d0032 镜像，跑 4h）致 `Conflict. The container name "/o-core" is already in use`，部署脚本无此检测，起报错即死。

## 钦定修法

- **deploy_image.sh 增 SG 侧 compose 同步步**：build 后、`docker compose up` 前 `scp` 本仓 `docker-compose.yml`+`docker-compose.sg.yml` 到 SG `/opt/o/`（先 diff 同则跳，异则备份 .bak-<sha> 再覆）。SG 侧文件从此只许此径更新，手工改=违例。
- **cpus 上限对齐宿主容量**：o-postgres `cpus: 8`→`4`（SG 实测核数）；o-postgres-test/o-core 的 `cpus: 4` 已贴线保留。同步考虑 cpus 值写成 `.env` 可覆写则更佳——施工评估，超域回填拒带理由。
- **残骸检测**：脚本 up 前 `docker inspect -f '{{index .Config.Labels "com.docker.compose.project"}}' o-core`——非本 project 标签→红字报「裸容器残骸，先人工处置」退出（不自动 rm，防误删在跑产件）。
- 票内附本次实部处置录：手工 scp compose 齐版+`--force-recreate o-core` 落产地锚 `.Config.Image=o-core:ab62c2f952af`，旧裸容器已 stop/rm。

## 验收锚

- 干跑实证：SG compose 与本仓异版时脚本先同步再 up；同版则跳。
- `docker compose -f docker-compose.yml -f docker-compose.sg.yml config` 在 SG 侧解出 `o-core` image 含 `${O_CORE_IMAGE}` 展开。
- 裸名容器桩测（docker 无 compose 标签容器存在时）→脚本按钦定报错退，不误删。
- cpus 修后 `up -d o-postgres`（或 `config` 校验）不再撞 CPU range 错——**真 recreate 验伤由决策席选窗执行，票内不自做**。
- `bash -n`+闸绿戳→支→PR→CI 绿→并。

## 边界

- 不改锁/出处闸语义（T-0217 已固）；只补 SG 侧缺口。
- cpus 降额对 PG 是放宽约束非收紧——风险向低，但 recreate 时点仍择窗。
- 双 -f 组合是钦定形态（base+sg overlay），同步两步都要带。

# 审批带宽保底缺位（唤知议程编排面实证）

**坑形**：proposed→裁定=决策席会话人工件（会话带宽是稀缺资源），
但唤知议程编排面（dispatch.sh trigger 组编）只有「有信号就唤」
没有「审批面保底」——救火信号（CI红族+landq污锁+mt5停册P1 连环）
可无限吃满唤知拍，审批队列只进不出：fin_opp_eval proposed 254 条
积压、最老龄 620h+，裁决族判词行（裁决/裁定/驳回/hypo decide）
连续静默 8h+ 无人处置。信号面越热闹，越没人裁标的——**热闹是
审批的天敌**。

**判别**：积压表（fin_opp_eval verdict='proposed'）计数只涨不降
∧ 裁决族判词行静默时长持续增长 ∧ 唤起拍数同期高企——三者同真
=审批带宽被救火吃满，非评估链病灶（产线活着，裁判席缺席）。

**修法**：议程编排面加「审批带宽保底」闸——积压最老龄>阈
（app_config 可裁）∧ 连续N拍零审批处置 → 议程因子出保底拍
（evalfloor），非P0救火件不挤、P0在飞（死刑/资金闸/对账/账链断
升件∪守位强平在飞）让位——救命恒先。落地=scripts/cognition/
evalfloor.sh + dispatch.sh trigger 并入 + runbook 议程保底条款。

**推广**：凡「人工/会话带宽裁决队列」与「机器信号触发队列」共用
同一稀缺资源（唤起拍/会话时长）的系统，编排面必须显式保底——
否则最响的信号永远赢，最重要的静默队列永远饿死。保底闸三要件：
①积压龄机读进议程因子（evalage_h）②零处置静默计数（eidle）
③救命件让位序写死不议价。

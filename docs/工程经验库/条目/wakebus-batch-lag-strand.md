# wakebus 批窗<滞后窗 strand（dispatch 唤起断链）

**坑形**：事件驱批处理器里，「通知即到、数据滞后」双窗失配——
NOTIFY 在 commit 时发出，但读行谓词带 `ts < now()-lag` 滞后窗
（防读早/防水位越过晚提交行）。批处理攒批窗 batch=6s < lag=15s：
NOTIFY 唤醒→等 6s→读行时该行 ts 龄仅 ~6s 仍被滞后窗挡下→本批
零行→**静默期无后续 NOTIFY**→该行永远等不到下一批（实证：
#34366 等 #34398 顺风车 17min；#34573/#34575 静默期 30min+ 零踹）。

**判别**：dispatch 媒体「落库即踹」承诺 vs 实际「落库+lag+batch+运气」；
症状=某些行被踹、相邻行长时间不动——差异不在内容在**到达时序**。
凡「谓词滞后窗>攒批窗」且「无独立周期扫」的事件驱循环皆同构病灶。

**修法**：漏唤兜底=件内周期补扫（本案裁案 a：sweepLoop 10s 拍
processBatch，最坏踹时 lag+sweep≈T+20s<钦定 26s 界；timer 案被否
——注册表/宿主实态三处一致成本高且 timer 粒度更粗）。滞后窗语义
保留；水位只推进到已处理行；晚提交小 id 行=滞后窗只防读早不防
读漏，须 `id>wm-lookback` 回看窗+seen 集去重兼收（否则 id≤wm
行被水位永久越过）。

**推广**：「事件驱+滞后窗+水位」三件套的正确不变量=**任何可见行
必在有限拍内被处理**——验收写成「单行+静默→限时踹」用例，桩测
必须走 DB 读行径（file 桩绕过滞后窗测不到本病灶）。
